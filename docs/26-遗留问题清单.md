## 1. 🔴 真 bug，仍在

### B1. EmuELEC 里按遥控电源键 → 休眠后**醒不过来**（需断电）

- 现象：`a4-ird` 把遥控电源键（`0x23dc4db2`）硬编码成 `fputs("mem", /sys/power/state)`；睡了之后按任何键都醒不来，只能断电。
- **换原厂 U-Boot 能不能解决？不能。** 实测证据（2026-10-20 22:44）：
  - 唤醒键表由**内核/msp 在运行时下发**，不是 U-Boot 里的数据——在 U-Boot 镜像里搜 `0x639cff00 / 0xef101980 / 0xf40b5da0` **0 命中**。
  - Android（3.10 内核）`/proc/hisi/msp/pm`：`IR WakeUp Key Number : 6`，**包含 `0x23dc4db2`**。
  - EmuELEC（4.4.35_ecoo）`/proc/hisi/msp/pm`：`IR WakeUp Key Number : 1`，**只有 `0x639cff00`**。
  - 而且设备现在**就在原厂 U-Boot 上**运行，所以"换 U-Boot"这个变量本身不成立。
  ⇒ 同一个 SoC、同一个遥控，Android 能唤醒、EmuELEC 不能，差别在各自内核下发的 PM 表。
- 可行修法（按代价排序）：
  1. **重编 `a4-ird`，把"电源键→休眠"改为可选（默认关）**——源码 `emuelec/work/ir/a4-ird.c:457`。
     ✅ **前提已满足（2026-10-21 09:05）**：现在有两支可用输入（`ZhiXu Gamepad` DInput + `A4 IR Remote`，且 `es_input.cfg` 同时存了 XInput/DInput 两份配置），改坏了不会失去操作能力。
  2. 改 EmuELEC 内核 PM 默认唤醒键（`hiir_ir2.h` 那套）——要重编内核，不现实。
- 临时对策：在 EmuELEC 里别按遥控电源键；要休眠用 ES 菜单的 shutdown（同样醒不来，至少不会误触）。
- **2026-10-21 09:05 现场复核仍然存在**：
  ```
  strings /storage/a4-ird | grep -c 'POWER KEY - suspending'  → 1
  strings /storage/a4-ird | grep 'power/state'                → /sys/power/state
  /proc/hisi/msp/pm: IR WakeUp Key Number = 1
                     IR WakeUp Key = High 32-bit(0x0), Low 32-bit(0x639cff00)   ← 不含 0x23dc4db2
  ```

### B2. 看门狗自愈被"永不失效的锁"卡死（`wifi_recover.sh`）—— ✅ **已修复（2026-10-20 22:46）**

- 原缺陷：`/system/bin/wifi_recover.sh:197` 用裸 `stat -c %Y`，设备只有 `busybox stat` → `stat: not found` → `m=0` → 陈旧锁分支永不进入 → 锁一旦残留就永久自愈失效。
- 修法（已落地）：`stat` → `busybox stat`；`rm -rf /data/local/tmp/wifi_recover.lock`（2016 年那个残留锁）。
- 现场验证：22:48:27 看门狗取锁 → 22:48:59 `eth0 RECOVER FAILED`（没插网线，预期）→ **70 秒后锁已自动释放**；同一份脚本此前从 22:43 一直卡到 22:49 不放锁。
- 备份：`/data/a4/wifi_recover.sh.orig-1020`。注意这属于 `/system` 改动，要固化到固件包才不怕重刷。

### B3. `init.bigfish.rc:94` 语法告警 —— ⏸ 未修，且不能在系统里改

- 实测：`sdcard_r` 单独成行 → `init: /init.bigfish.rc: 94: invalid option 'sdcard_r'`。
- 为什么没改：`/init.bigfish.rc` 在 **boot ramdisk（p11 boot.img）** 里，运行时改了也只是内存副本，重启即还原。要固化必须重打包 `boot.img`。
- 影响：仅启动日志一行告警，无功能影响 ⇒ 放下次出固件包时顺手改。

### B4. `a4-hotplug` 缓冲区溢出崩溃 —— ✅ **已修复（2026-10-20 23:07）**

- 证据：`/storage/ee/logs/a4-hotplug.log` 出现 3 次 `*** buffer overflow detected ***: terminated`（glibc `__fortify_fail`）。崩溃后**没有任何机制重新拉起它**，热插拔彻底失守。
- 设备上跑的二进制 md5 `30409bee`(379,312B) 与本地源码产物 `cd37f279`(379,272B) **不是同一构建**。
- 崩溃时机：收到 inotify 事件、进入 `is_physical_joystick()` 时（日志只有 `watching`，从未出现 `added:`）。
- 修法：遍历 inotify 缓冲区时校验「剩余长度 ≥ 一个完整事件」，不足则丢弃尾部并 break；`ev->len` 参与步进计算。

### B5. 重启链路整体失效（`S95emuelec restart` 的 "already running" 短路）—— ✅ **已绕过**

- `start_frontend()` 里：
  ```sh
  if [ -f /var/run/histb-emuelec.pid ]; then
      old_pid=$(cat ...)
      kill -0 "$old_pid" && return 0      # 直接跳过，不重启
  fi
  ```
- 而实测该 pid 文件内容是 **ES 的 pid（2760）**，真正的 supervisor 是 **1836** ⇒ 每次 restart 都判定"已在运行"，**ES 从未被重启**。
- `a4-hotplug` 与 `a4-inputwatch` **都调这条命令**，所以两条路一起废。这是"手柄热插拔后 ES 重启不生效"的直接原因。
- 修法：守护进程不再走 S95，改为**直接对 ES 进程发 SIGTERM**（8 s 不退再 SIGKILL），supervisor 会自动重拉（实测 3~5 s。）

### B6. `strstr` 落在 NUL 分隔的 cmdline 上，永远找不到 ES —— ✅ **已修复（2026-10-20 23:13）**

- `/proc/<pid>/cmdline` 是 `argv[0]\0argv[1]\0...`，`strstr(buf, "/emulationstation")` 遇到第一个 `\0` 就停，只能看到 `/lib/ld-linux.so.3`。
- 后果：每次插拔都打印 `no frontend running, nothing to do`，**检测到设备却什么都不做**；ES 继续持有已删除 inode 的 fd（`/dev/input/event1 (deleted)`），手柄灯亮但按键完全无响应。
- 修法：读入后把 `\0` 全部替换成空格再 `strstr`；并加一次 1.5 s 重试（supervisor 可能在重启 ES 的瞬间）。
- 附带加固：**启动时**检测 ES 是否已持有 `(deleted)` 的 input fd，若有则主动重启一次，把已经处于"聋"状态的机器救回来。

## 4. 已知局限（设计取舍，不算 bug）

- IR 遥控**不支持长按连滚**（有意：该控制器状态位无法可靠区分长按重复帧，做连滚会重新引入误步进）。
- 换遥控器需重新 `learn` 并手改 `keys.map`，**无界面**。
- 音量键在 ES 里绑成整页翻页，**游戏内调音量**没做。
- GPU 频率锁 200 MHz 不可调（`pm_gpu` 的 volt/freq/dvfs 均为 no-op）；再压温度需查 core/DDR 联动，有挂机风险。
- H.263 解码槽位被 AVS 占用 → H.263 失效（已确认可接受）；AVS 扩展件已备未部署（无片源）。
- `p13`(backup) 被 EmuELEC rootfs 占用 → 安卓的 backup 分区实际不存在；全量包会 format 它（见 B4）。

### B4. 操作风险（不是 bug，但会毁数据）
- `update_hisi_full_v2.zip`（311MB）会 `format system / cache / backup(p13=EmuELEC) / userdata`，**把 EmuELEC 和 /data 一起清掉**。
- 日常救砖只用 TF 卡上那个 8.35MB 小包（只写 p11+p2）。
