> 基线：`update.zip`（原厂，292 MB，1598 条目，AOSP testkey 签名）
> 日期：2026-10-29

## 1. 核心原理

原厂 OTA 的 `updater-script` 里有这么一段：

```edify
format("ext4", "EMMC", "/dev/block/platform/hi_mci.1/by-name/backup", "0", "/backup");
mount("ext4", "EMMC", "/dev/block/platform/hi_mci.1/by-name/backup", "/backup");
package_extract_dir("backup", "/backup");
unmount("/backup");
```

而 **安卓的 `backup` 分区（p13）正是 EmuELEC 的 rootfs 所在块**（U-Boot 里的
`blkdevparts` 明确写着 `340M(backup)`，偏移 102 MiB；EmuELEC 侧对应 `/dev/mmcblk0p9`
即 `340M(storage)`，`root=/dev/mmcblk0p9`）。

⇒ **刷原厂包时这一步 `format backup` 就是在抹掉 EmuELEC**，所以双系统刷没了。

本包把这一步换成直接写入 EmuELEC 的 rootfs 镜像：

```edify
# ---- A4: backup 分区（=EmuELEC rootfs）写回系统镜像，不再 format ----
package_extract_file("emuelec_rootfs.img", "/dev/block/platform/hi_mci.1/by-name/backup");
```

**`fastboot`(p1) 和 `factory`(p10) 一行都不动**，所以：
- U-Boot 里的双系统切换逻辑保持（不会被原厂 U-Boot 覆盖）
- EmuELEC 内核（p10）保持
- 只更新 rootfs，双系统结构不变

## 3. 打包过程中踩的坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 长文件名折行 | `parse_manifest_order` 解析出 20 个截断名（`buttonfocus.p`），与原 zip 条目对不上，直接 ABORT | JAR 规范每行 72 字节，长名用 `\r\n ` 续行。改为**保护原格式**：逐段解析时展开续行取真名，只替换摘要值（等长），不重新排版 |
| CERT.SF 字段名 | 老脚本写的是 `SHA1-Digest`，原包实际是 **`SHA1-Digest-Manifest`** | 反推原包验证：`sha1(MANIFEST 该段完整字节，含末尾 \r\n\r\n)` == SF 里的值，逐字节匹配 |
| 段分隔符 | 老脚本按 `\r\n\r\n\r\n`（三个 CRLF）切分，实际是**一个空行**（`\r\n\r\n`） | 按 `\r\n\r\n` 切分，每段补回末尾 `\r\n\r\n` 再算 SHA1 |
| `cryptography`/`asn1crypto` 缺失 | 重签直接 ImportError | `pip install asn1crypto cryptography`（默认源可用，清华源反而找不到） |

**回放校验**：`python tools/repack_ee2.py --dry` —— 不替换任何文件时，
生成的 MANIFEST 与原包**逐字节一致**、SF 头一致，证明算法正确。

### 7.2 为什么用 ee_files 而不是重做镜像

rootfs 镜像 340MB，导一次要 8 分钟（分段 dd + 逐段下载 + 拼接）。
小改动没必要重导——在 `updater-script` 里写完镜像后，再：

```edify

```

以后 EmuELEC 侧的小改动都走这条路。

### 7.3 降压策略变更（按用户要求）

**旧**：`init.bigfish.sh` 里写死 `echo volt=1080 > /proc/hisi/msp/pm_cpu` 等，
开机无条件执行（除非存在 `/data/local/tmp/uv_disable` 这个"反向开关"）。

**新**：

```sh
# init.bigfish.sh
if [ -x /system/xbin/a4-uv ]; then
  /system/xbin/a4-uv boot
fi
```

`a4-uv boot` 读 `/data/a4/uv.conf` 的 `AUTO`：

- `AUTO=0`（**默认**）→ 什么都不做
- `AUTO=1` → 应用降压

手动控制：

```sh
su -c 'a4-uv on'      # 立即降压（1.0GHz@1080mV + core 1000mV，AVS off）
su -c 'a4-uv off'     # 恢复（AVS on，1.5GHz）
su -c 'a4-uv auto on' # 设为开机自动
su -c 'a4-uv status'  # 看频率/电压/温度/开关状态
```

### 7.4 WiFi 策略变更（按用户要求）

`gen_conf()` 现在**只从安卓读**：

```
安卓读不到  → 保持现有 supplicant 不动（不清空，不会把已有的网搞丢）
安卓没有网络 → 同上
安卓有网络  → 全部导入，覆盖 supplicant
```

`wifi.conf` / `emuelec.conf` 的 wifi.ssid 不再参与生成。

> `a4-wifi set <SSID> <密码>` 现在的定位变成"应急手动写入"，
> 正常流程完全不需要它。

### 8.6 App 如何在不 root 的情况下改电压

`su` 是本 ROM 的 SuperSU 版（`-rwsr-sr-x`），但**没装 SuperSU 管理器** ⇒ 应用请求 root
被静默拒绝（双系统 App 当年就是因此改成"请求文件"方案，见 `/data/a4/a4-switchd` 头注释）。

所以 A4Tune 复刻同一套协议：

```
/data/a4/uv.request    App 写（目录 0777）
                       ↓ 2 秒轮询（root）
/system/xbin/a4-uv watch  → 改 cpufreq / pm_cpu / pm_core → 写 /data/a4/uv.status
                       ↓
                    App 读 status 刷新界面
```

守护由 `/system/etc/install-recovery.sh` 用 `busybox setsid ... while true` 启动
（必须 setsid：init 在 oneshot 脚本退出时会 kill 整个进程组，这是 2026-10-21 踩过的坑）。

### 8.7 请求链路实测（WSL 沙箱，root 身份）

把 `a4-uv` 里的路径 sed 成临时目录（`/tmp/uvtest2/d`、假 `pm_cpu`/`pm_core`/`cpufreq`），
以 root 跑 `watch`，再用 `echo on > uv.request` 模拟 App：

```
10-29 11:52:58 watch: started (pid 90)
10-29 11:53:00 request: on
10-29 11:53:02 on: cpu=1000MHz/1080mV core=1000mV
10-29 11:53:04 request: auto-on      → AUTO=1（conf 与 status 同步）
10-29 11:53:08 request: off           → restored avs on, max 1.5GHz ondemand
```

副作用核对：`scaling_governor=performance`、`scaling_min_freq=1000000`、`scaling_max_freq=1000000`、
`pm_cpu` 写入 `volt=1080`、`pm_core` 写入 `volt=1000`，`uv.status` 字段齐全，请求文件被消费。

> 顺带修了一个真 bug：早期 `need_root()` 里是 `exit 1`，一旦非 root 触发会把 **watch 守护本身**带走。
> 已改成 `return 1` + 在 `run_request` 里先判断 uid，守护不会被请求内容打死。

## 9. v4：刷入立即失败的根因 —— **缺 jared 整包签名**（已修复）

### 9.1 症状与证据

刷入瞬间失败（还没执行任何脚本）。对比原厂包与 v3 包：

```
update.zip            EOCD 注释长度 = 1738   注释开头 = "signed by SignApk\0" + PKCS7
update_a4_dual.zip    EOCD 注释长度 =    0   ← 没有整包签名
```

海思 recovery 的 `verify_file()` 走的是 **jared（整包）签名**校验：
它读取 ZIP **末尾注释**里的 PKCS#7，用其中证书对"除注释外的整包字节"做 RSA 校验。
注释长度为 0 ⇒ 直接判签名失败 ⇒ 立即中止。

v2/v3 用自己拼 `MANIFEST.MF / CERT.SF / CERT.RSA` 的 jar 逐条目签名，
**这只满足 APK 的校验方式，不满足 OTA 的整包校验**——这是刷不进去的真正原因。

### 9.2 修复：改走标准流程（signapk -w）

新脚本 `tools/repack_ee3.py`：

1. 只写数据条目（**不含 META-INF 签名文件**），保持原包顺序与压缩方式；
2. 调 AOSP 的 `signapk.jar -w` 生成 MANIFEST/SF/RSA **并追加整包签名**：

```bash
java -jar /home/mxz/aosp/out/host/linux-x86/framework/signapk.jar -w \
     keys/testkey.x509.pem keys/testkey.pk8 \
     update_a4_dual.unsigned.zip update_a4_dual.zip
```

### 9.3 校验（不是看字符串，是真验签）

注释结构（来自 `SignApk.java signWholeFile()`）：

```
comment = "signed by SignApk"(17) + 0x00 + PKCS7(1714) + sig_start(2) + FFFF + total_size(2)
总长 = 1714 + 24 = 1738
签名覆盖 = 文件 [0, EOCD+20)  —— 即除注释长度字段与注释外的全部字节
```

实测：

```
整包签名(jared): PASS   size 368.6 MB  注释 1738 B
条目 1612，MANIFEST 覆盖 1609，缺失 0（3 个是 META-INF 自身）
updater-script: package_extract_file("emuelec_rootfs.img", ".../by-name/backup");
硬解 so md5 1f6a8757
```

### 9.4 教训

- **OTA 包 ≠ APK**：OTA 必须**整包签名（jared）**；自己拼 MANIFEST 只够 APK。
- 判断方法很便宜：`xxd` 看文件最后 22 字节前的注释长度字段，原厂是 1738，没有就是 0。
- 以后一律用 `repack_ee3.py`（signapk -w），不要再手工拼签名。

## 10. v5：两个致命问题（刷进去后切不到 EmuELEC）

### 10.1 p1（U-Boot）被原厂镜像覆盖

原厂 updater-script 里有一行：

```edify
ifelse(getprop("persist.sys.packagetype.qfp") == "true",
       package_extract_file("fastboot-qfp.img", ".../by-name/fastboot"),
       package_extract_file("fastboot.img",    ".../by-name/fastboot"));
```

**它会把 p1 写成原厂 U-Boot**。而我们的双系统只是"原厂 U-Boot + mode2 的 cmdline 补丁"
（p1 偏移 `0x79440` 起 216 字节，cmdline 里带 `root=/dev/mmcblk0p9`）。
原厂 U-Boot 的 mode2 cmdline 没有 `root=`，于是 `misc=product-test` 标记形同废纸 ⇒ 永远进 Android。

实测（刷完后读设备）：

```
设备 p1 前 64K md5 = 43733a5cf81334ecbad66f617f14c739  ← 等于原厂 fastboot.img
我们的双系统 U-Boot  = fb850755194cee1a7508f33ad1939cb2（fastboot_cmdonly_hinas.bin，618 444 B）
```

**修法**：包内新增 `fastboot_a4.img`（= 上面那份），updater-script 直接写 p1，不再用原厂那两行。

### 10.2 rootfs 镜像是"脏"的 —— 内核回放日志后文件系统坏掉

`emuelec_rootfs.img` 是从**正在运行的 EmuELEC** 上 `dd` 出来的，所以：

```
e2fsck -fn   → 只有 superblock 计数不一致（看起来没事）
mount -o rw  → "Structure needs cleaning"     ← 真正的问题
e2fsck -fy   → 回放日志后变成 11 个文件（数据被日志"回滚"掉了）
```

即：镜像里带着 `needs_recovery` 的旧日志，内核启动时回放日志 → 文件系统结构被破坏 → rootfs 挂不上 → EmuELEC 起不来。

**修法**（离线修，不动内容）：

```bash
cp emu_rootfs.img emu_rootfs.clean.img
debugfs -w -R "feature ^has_journal" emu_rootfs.clean.img   # 丢掉那本坏日志，不回放
e2fsck -fy emu_rootfs.clean.img                             # 修计数
```

结果：`2252/24384 files`，`mount -o rw` 正常，能 touch/删除，ES md5 仍是 `ff8f5b13`（补丁版），
`a4-hotplug`/`a4-ird`/`S93wifi` 都在。包里已换成这份 `emu_rootfs.clean.img`。

> **教训**：从运行中的系统抓镜像，必须先 `sync; mount -o remount,ro /`，否则日志是脏的；
> dd 完再跑一遍"去日志 + fsck"最稳。之前只看了 `53ef` 魔数就以为 OK，是错的。

### 10.3 顺带：切换脚本搬到 `/system/xbin`

之前放在 `/data/a4`（`format userdata` 会清，靠包里 `userdata/a4/` 放回）。
现在改为：

| 文件 | 位置 |
|---|---|
| `a4-switchd` / `a4-os-switch` / `switch-to-android` / `switch-to-emuelec` | **`/system/xbin/`**（刷机后必在） |
| `/data/a4/` | 只放运行期文件：`uv.conf`、`uv.status`、`switch.request`、`*.log`、`misc.bak` |

`install-recovery.sh` 优先用 `/system/xbin/a4-switchd`，缺了才回退 `/data/a4`。

## 11. v6：切换真正跑通（Android ⇄ EmuELEC 双向实测）

### 11.1 真正的根因：`a4-switch` 还在读 `/data/a4/env-*.bin`

老版 `a4-switch`（`/system/xbin/a4-switch`，setuid 4755）是"把 `env-android.bin` / `env-emuelec.bin`
写进 p2(env)"的实现。这两个 bin 原本放在 `/data/a4/`，而 `format userdata` 每次都把 `/data` 清空
⇒ 文件没了 ⇒ `refusing to switch` ⇒ App 里点"切到 EmuELEC"完全没反应。

更关键：**这台机器的原厂 U-Boot 根本不读 env 的 bootcmd**，只有 misc 三档模式有效
（`product-test` / `boot-recovery` / 空）。旧方案从原理上就不可能工作。

### 11.2 重写：只写 misc 前 32 字节

`tools/a4-switch.c` → 静态链接 ARM 二进制（md5 `8dffad77`），
与 `/data/a4/a4-os-switch` 完全同源同行为，但不再依赖任何 `/data` 文件：

```
a4-switch emuelec    misc[0..32] = "product-test"  → 重启进 EmuELEC
a4-switch android    清零                          → 重启进 Android
a4-switch recovery   "boot-recovery"               → 重启进 recovery
a4-switch status     读回指示
```

安装权限必须是 **4755（setuid）**：`rwsr-sr-x 1 0 0`。
`install-recovery.sh` 里原来写着 `chmod 0755 /system/xbin/a4-switch`，
每次开机都会把 setuid 抹掉 ⇒ App（非 root）调用时写不了 misc。已改成 `chmod 06755`。

### 11.3 双向实测（不是看代码，是看系统真的换了）

```
[Android] 写 misc = product-test → 重启
  → uptime 340s，uname 4.4.35_ecoo_81082668，/opt/emuelec 存在  = EmuELEC ✔
  → rootfs /dev/root 挂在 / (ext4 rw)，ES pid 1965，TF 卡 10 个 ROM
[EmuELEC] /usr/bin/a4-os-switch android → 重启
  → adb 在线，/data/app 能读 = Android ✔
  → p13 头 64K md5: 9868195a… → 8d93a64f…  (EmuELEC 确实 rw 挂载写过 rootfs)
```

再用**纯遥控器**（只有 keyevent，没有任何触摸）走 App 路径：

```
打开 com.a4.switcher → ① 已是琥珀选中 → 按 OK
  → /data/a4/switch.request=emuelec → a4-switchd(root) → misc=product-test → 重启
  → 80 秒后在 EmuELEC 里 telnet 通，uptime 78s  ✔
```

### 11.4 顺带发现：`install-recovery.sh` 必须随包

`updater-script` 第 2 行就是 `format("ext4", … by-name/system …)`，之后按本包的
`system/` 树重铺。原厂那份 `install-recovery.sh` 只有 30 行 —— 没有 a4-switchd 守护、
没有 `a4-uv boot`、没有 setuid 修复。**如果包里不带这份，一刷机切换就全废**。
