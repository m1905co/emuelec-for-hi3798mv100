## 2. 问题一：HDMI 永远输出 720p60

### 2.1 现象（用户描述精确化）

> "设置里设 1080p60，软件按这个尺寸展开，电视也以为在按 1080p60 协商输出；但**从 HDMI 接口实际抓出来的内容是 720p**——软件侧 1080p 非常清晰，硬件侧抓出来差一大截。"

即：**声明层是 1080p，物理层是 720p**。

### 2.2 三轮定位历程

| 轮次 | 假设 | 结论 |
|---|---|---|
| 第一轮 | `baseparam` EDID 全零 → `GetSinkCapability` 返回 -1 → 兜底 720p | **部分成立**：EDID 确实为空，但没有解释"软件以为 1080p"的矛盾 |
| 第二轮（实测） | HDMI 未插线 → `Output Mode: DVI`、`EDID Unvalid`、`VirtualScreen` 回落 720p | **发现关键解耦**：`disptest setfmt 0`（改 `ENC_FMT`）成功后，`VirtualScreen`/`hifb` **纹丝不动**——两条通路独立 |
| 第三轮（反汇编） | 谁把虚拟屏钉死在 720p？ | **找到代码级元凶**：`HDMI_HotPlug_Proc` 只调 `set_format`，从不调 `set_virtual_screen` |

### 2.3 ★ 决定性根因（代码级）★

对 `/system/lib/hw/hidisplay.bigfish.so`（38,292 字节）逐函数反汇编，得到调用图：

```
set_virtual_screen  <── reload  @0x4022
                    <── reset   @0x42bc     ← 全库只有这两处调用

set_format  <── reset            @0x42c2
            <── setOptimalFormat @0x4d96
            <── HDMI_HotPlug_Proc @0x575c   ← 热插拔！
            <── HDMI_HotPlug_Proc @0x579c   ← 热插拔！
            <── HIADP_HDMI_Init  @0x6188
```

**`HDMI_HotPlug_Proc`（HDMI 热插拔/协商完成回调）里只调 `set_format`（改编码格式），一次都不调 `set_virtual_screen`。**

于是：

1. 插 TV → `HDMI_HotPlug_Proc` → `setOptimalFormat` → `set_format(1080P60)` —— **只改编码格式，虚拟屏不动**；
2. 虚拟屏只在**开机 `reload`/`reset`** 那一次被设过，之后**再没人动它**；
3. 结果：HDMI TX 按 1080p 发 TMDS（声明层、TV、上层软件全看到 1080p），但送进 TMDS 的画布来自 `hifb` 图形层，尺寸仍是开机时定下的 **1280×720**。

→ **"1080p 的时序 + 720p 的内容"**，与现象完全吻合。这不是"协商失败"，是**热插拔路径漏掉了虚拟屏同步**——架构级缺陷。

### 2.4 支撑证据

**证据 1 —— `set_virtual_screen`@`0x3bac` 只有两档硬编码（HAL 本身有能力出 1080p）**

```asm
003bfa  cbnz   r6, 0x3c08        ; 参数 mode（r0）
003bfc  mov.w  r0, #0x500        ; 1280
003c00  mov.w  r1, #0x2d0        ;  720
003c08  mov.w  r1, #0x438        ; 1080
003c0c  mov.w  r0, #0x780        ; 1920
```
→ `mode==0 → 1280×720`；`mode!=0 → 1920×1080`。与 `get_virtual_screen()`@`0x284d` 用同样魔数比回来，严格对称。**代码里就写着 1920×1080。**

**证据 2 —— 开机 `reload`@`0x3fd8` 怎么选档**

```asm
003fde  movs  r0, #1
003fe0  add   r1, sp, #8
003fe2  blx   #0x240c            ; HI_UNF_PDM_GetBaseParam(1,&buf)
003ffe  ldr   r0, [sp,#0x10c]    ; buf.VirtScreenWidth
004008  subs.w r0, r0, #0x500    ; -1280
00400e  it ne
004010  movne r0, #1             ; width!=1280 → mode=1 → 1080p；否则 0 → 720p
004022  bl    #0x3bac            ; set_virtual_screen(mode)
```
开机分支本身正确；但 baseparam 里存的是 **1280**，于是走 720p 分支，而热插拔又不再更新 → 永远 720p。

**证据 3 —— 还有一条 `ro.config.low_ram` 强制钳位**（`disp_init`@`0x4559`）
若 `ro.config.low_ram==true` 且虚拟屏≠1280×720，则 `HI_UNF_PDM_UpdateBaseParam(1,…)` **写回 baseparam** 并 `HI_UNF_DISP_SetVirtualScreen(1,1280,720)`。本机 `ro.config.low_ram` 为空、内存 1GB，**未触发**；但它证明了这套 HAL 有"主动钳位到 720p 并持久化"的行为模式 —— 也解释了为什么单改 baseparam 容易被覆盖。

**证据 4 —— baseparam 的 DISP1 配置其实是对的**

重新逐字节解析 `out/baseparam_device.bak`（格式：**32 字节键名 + 4 字节长度 + 4 字节值 = 40 字节/项**）：
```
DISP1 表 @0x824（表长 0x7f8）:
  0x848  BASE_KEY_SOURCE_DISP  = 1
  0x870  BASE_KEY_FMT          = 0     ← FMT_1080P_60，本来就是对的
  0x898+ BASE_KEY_TIMING_*     = 全 0  （走标准时序表）
```
**DISP 表里没有独立的"虚拟屏"键** → "往 baseparam 写一个虚拟屏键"这条路不存在。

**证据 5 —— 内核驱动能力上限远高于 720p**
vmlinux 字符串：`'screen window too small ,must be within [480,3840].'`、`'Invalid vir screen:W %d, H %d'`。
→ **720p 不是驱动上限，是 fallback 默认值。**

**证据 6 —— `PDM_GetMaxScreenSize(fmt)` 查表（`libhi_msp.so`@`0x27d84`，Thumb `tbb` 跳转表）**

| fmt | 结果 | fmt | 结果 |
|---|---|---|---|
| 0 (1080P60) | **1920×1080** | 11 (PAL) | 720×576 |
| 7 (720P60) | 1280×720 | 22 (640×480) | 640×480 |
| 9 (576P50) | 720×576 | 25 (1280×720) | 1280×720 |
| 10 (480P60) | 720×576 | 40 (2048×1152) | 2048×1152 |

理论上 `fmt=0` 就该给 1920×1080，但 `PDM_GetDispParam` 开机读一次即缓存，热插拔后无人再调 → 该表形同虚设。

### 2.5 设备实测佐证

```
# disptest setfmt 0 → getfmt = 0（确认已是 FMT_1080P_60）
/proc/hisi/msp/disp1     Formt/DispMode : 1080P60/2D
                         VirtualScreen  : 1280/720      ← 纹丝不动
/proc/hisi/msp/hifb0     Resolution(real/virtual/max) : (1280,720)/(1280,2160)/(1280,720)
                         DisplayResolution : (1280,720) ← 没变
/sys/class/graphics/fb0/modes : U:1280x720p-0 / U:0x0p-0  ← 只注册了 720p
/proc/hisi/msp/hdmi0     Out Timing : 2200x1125（=1080p60 标准 H/V Total）
                         TMDS Clock : 148.5 MHz
                         Video ID   : 0x10 (=16=1080p60)
```
**HDMI 声明层完全正确（2200×1125 / 148.5MHz / VIC 0x10），但画布锁 720p** —— 决定性证据。

另外 `echo output 1 > /proc/msp/hdmi0` 可把 `Output Mode: DVI` 纠正为 `HDMI`、`EDID Status: Unvalid→Valid`、`Pixel Clk: unstable→stable`，但 **`VirtualScreen` 仍 720p** —— 再次证明两者解耦。

### 2.6 修复路径（三选一，按可直接验证程度排序）

| 方案 | 做法 | 是否需刷机 | 风险 |
|---|---|---|---|
| **A（最短路径）** | 直接调 Binder，触发 `DisplayService::setVirtScreen(1)` → 走 `mode=1` 档 → 1920×1080 | 否，当场可验 | 低 |
| **B（根治）** | 在 HAL `set_format` 里补一次 `set_virtual_screen`，让"改格式"与"改虚拟屏"绑定；重打 `hidisplay.bigfish.so` | 是 | 中 |
| **C（持久化）** | 让开机 `reload` 读出非 1280 从而走 1080p 分支 | 是 | 高（证据 4/3：无独立键 + 可能被钳位） |

**已知服务与接口（供方案 A 用）**：
- 服务名 **`HiDisplay`**（`dumpsys HiDisplay` 可用，输出 `Format:0` + 能力表）
- `DisplayService::setVirtScreen` @ `libhidisplayservice.so:0x6152`
- Binder 入口 `BnDisplayService::onTransact` @ `0x6c4d`（`tbh` 跳转表在 `0x6c6a`，事务码 1..0x2c）
- 客户端 `DisplayClient::setVirtScreen` @ `libhidisplayclient.so:0x4e31`（经 vtable `[r3,#0x8c]`）

**已试无效**：遍历 `service call HiDisplay {15..25} i32 1` 全部未改变 `VirtualScreen` → 说明这些 code 不是 `setVirtScreen`，或该事务需多参数/前置条件。**下一步需从 `onTransact` 的跳转表精确定位该事务码**（或反汇编 `BpDisplayService` 的 vtable slot `0x8c` 读其 `transact(code,…)`）。

**已证无效的旁路操作**：`echo 1920x1080p-0 > fb0/mode`（只读）、`disptest setrange`（失败）、改 `persist.sys.display.*`、重启 `displaysetting`（开机走 `disp_init→reload`，不读 `persist.sys.display.param`）。

## 3. 问题二：ijk 硬解 4K H.265 失败 + 白滤镜

### 3.1 目标与真实栈

- 目标 App：**com.bilibili.tv**（唯一含 ijkplayer 的包，so 在 `/data/app-lib/com.bilibili.tv-1/`）。
- 厂商播放器：**MediaCenter.apk 内 `.so` 数量 = 0**（zipfile 遍历 330 项）——它完全**绕开 MediaCodec**，走私有栈
  `libhimediaplayer_jni.so → libhiplayer_adapter.so → libhi_msp.so`（`HI_UNF_AVPLAY_*`），直连 `/dev/hi_omxvdec`。
- **这是两套并行栈**，ijk 作为普通应用吃不到厂商能力 → 架构天花板。

### 3.2 根因 A：框架层没有注册 HEVC（硬解失败的直接机制）

| 检查项 | 结果 |
|---|---|
| `/system/etc/media_codecs.xml` | 全 文 无 `hevc`（`OMX.hisi.video.decoder` 只声明 mp4v-es/3gpp/**avc**） |
| `libstagefright.so` mime→role 静态表 @`0xca837`–`0xca8df` | **缺 `video_decoder.hevc`** |
| `libstagefright.so` mime 字符串表 @`0xd70a0` | 无 `video/hevc`（全库计数 0） |
| HEVC 软解兜底 `libstagefright_soft_hevcdec.so` | **不存在** |
| **底层 role（OMX）** | **有！** `libOMX_Core.so`@`0x1a64`、`libOMX.hisi.video.decoder.so`@`0x5edc` 均含 `video_decoder.hevc` |

**机制**：底层 VDEC 硬件支持 HEVC，但 Android 框架的 mime→role 映射表里没有 hevc → `MediaCodec.createDecoderByType("video/hevc")` 直接失败 → ijk 的 `ffpipenode_create_video_decoder_from_android_mediacodec` 走不通。

**已排除**：设备节点权限 OK（`/dev/hi_omxvdec` = `crw-rw---- system audio`，mediaserver Gid 含 1005=audio）；ABI 匹配（ijk 为 ARM 32bit EI_CLASS=1，CPU 为 ARMv7）。

### 3.3 根因 B：白滤镜 = 合成层问题，不是解码层

**现象特征**：均匀、半透明、盖住画面 → 符合"多一层合成 / alpha 混合"，而非"像素格式解释错（会是偏色/花屏）"。

证据链：
- 本机 overlay 只认 **YV12**（`gralloc.bigfish.so` 唯一明文格式串 @`0x1cc8`，其余 rodata 已混淆）
- hwcomposer 是 **TDE2 硬件合成**（`hwcomposer.bigfish.so` 导入 `HI_TDE2_Open/BeginJob/QuickFill/Bitblit/EndJob`）
- ijk MediaCodec vout 输出 `FormatSurface`/RGBA 类格式（`ijksdl.so` 内置格式名表 @`0x33680`–`0x339f0`）
- 两边的失败日志点都在：ijk `unknown overlay format: %d`@`0x32a24`、`unknown hal format %d`@`0x32ab4`；合成侧 `getBpp fail format is %d`@`0x1b51`、`fb2TdeFmt fail!format[%d]`@`0x1c69`、`QuickFill Failed`@`0x1ca3`

**机制（强推断）**：ijk 渲染帧 → SurfaceView/BufferQueue → hwcomposer `tde_compose` → 因格式不被 overlay 识别，走 `TDE2_QuickFill`（填充）或 blend 分支 → 用未初始化 buffer 参与合成 → 视频层上方出现白色/半透明遮罩。**该机制与解码来源无关，所以软解/硬解都可能出现白滤镜。**

**已排除**：gralloc 分配失败（SurfaceFlinger 各 layer 正常）、DRM 干扰（`drm.client.enabled=false`）、overlay 模块缺失（`liboverlay.so` 正常导出 `HI_MPI_WIN_*`）。

### 3.4 修复方案（三档）

**第一档 · 改配置（优先）**
- **D1-1**：`media_codecs.xml` 给 `OMX.hisi.video.decoder` 补 `<Type name="video/hevc" />`（风险中：`libstagefright.so` 静态表仍缺 hevc，可能只改 xml 不够）
- **D1-2**：改完推设备，`logcat` 抓 `hevc|OMX.hisi|mediacodec` 验证 mime 是否真命中
- **D1-3**：ijk 参数 —— `mediacodec`、`mediacodec-avc`、`mediacodec-all-videos`、`mediacodec-default-{avc,hevc}-name=OMX.hisi.video.decoder`、`hw-decode-fallback-enable`、`async-init-decoder`
- **D1-4（临时消白滤镜）**：关 `mediacodec` 让其走 `libijkffmpeg` 软解 + GLES2 vout，绕开 overlay 原生路径

**第二档 · 改 APK 渲染路径（中）**
- **D2-1**：ijk 改用 **TextureView + GLES2** 合成视频层（绕开只吃 YV12 的 overlay）
- **D2-2**：把 MediaCodec 颜色格式候选**收敛到 I420/NV12**（软解路径已有 `--overlay-format= fcc-i420/fcc-yv12`）
- **D2-3**：直接对接厂商 `libhiplayer_adapter.so` 的 `HI_UNF_AVPLAY_*`（工作量大）

**第三档 · 改固件 so（高）**
- **D3-1**：给 `libstagefright.so` 补 hevc mime/role 映射（需 ARM 反汇编 + 重建 + 重签）
- **D3-2**：扩展 gralloc 支持所需 pixel format（rodata 已加密）
- **D3-3**：放宽 `libOMX.hisi.video.decoder.so`@`0x5fc9` 的 4K 分辨率门限
- **D3-4**：让 ijk 改走已被 `HiMediaPlayerFactory` 接管的 `MediaPlayer` 体系

**推荐顺序**：D1-3 + D1-4（零风险）→ D1-1 + D1-2 → 不生效则 D2-1/D2-2 → 4K 仍被拒则评估 D3。

## 4. 问题三：休眠唤醒后 adb 连不上 / WiFi 异常

### 4.1 四个颠覆原假设的实测结论

1. **adb 走的是 eth0 有线，不是 wlan0。** 【实测】默认路由与全部 ARP 条目都在 eth0。→ 失效点是 **eth0 链路 / eth0 的 DHCP 租约**，与 WiFi 无因果关系。
2. **wlan0 休眠前就已 carrier=0、无 IP、收发全 0** —— 根本没连着。【实测】
3. **网卡是 RTL8188EU**（`rtl8188eu.ko` v4.3.0.8），不是 8188F。dmesg 里 `Link is Up 100/Full` 是 **eth0 的 himii PHY** 正常协商结果，错误计数全零，**不是异常**。
4. **唤醒源仅红外遥控**。【实测】`/proc/msp/pm`：`Ethernet WakeUp: Disable`、`USB WakeUp: Disable`、`IR WakeUp Key Number: 6`。→ 这是所有方案的安全约束。

### 4.2 根因排序

| 排名 | 假设 | 结论 | 置信度 | 关键证据 |
|---|---|---|---|---|
| 1 | init 层无 resume 钩子，supplicant/dhcpcd 无守护重启 | **成立·主因** | 高 | 6 个 .rc 文件 `on resume` 类命中 **0**；`init.bigfish.rc:97/222` 定义了 `iprenew_eth0/wlan0` 却**无人 start** |
| 2 | DHCP 未重新获取 | 成立 | 高 | dex `releaseDhcpLease`；adb 依赖 eth0 IP；`ro.thirdparty.dhcp=false` |
| 3 | 休眠前框架主动关 WiFi/释放租约，恢复不对称 | 成立 | 高 | HiRMService dex `"Wifi is on, Turn off Wifi && set wifi_saved_state to 1."` |
| 4 | 唤醒源受限（仅 IR） | 成立·约束 | 中高 | `/proc/msp/pm` |
| 5 | 驱动 suspend/resume 失败 | 待验证 | 低 | `rtl8188eu.ko` 有完整 `rtw_suspend/rtw_resume`，但 dbg 计数器未导出，无法证实 |
| 6 | 网卡 down 无人 up | 不成立 | — | `flags=0x1003` 含 IFF_UP；eth0 carrier=1 |
| 7 | `init.bigfish.rc:94 sdcard_r` 语法错误毁掉后续配置 | **已证伪** | — | `init.svc.blueangel=running`；其后 10+ service 全 running |
| 8 | HDMISuspend 与 PM 冲突 | 无证据 | — | 未见耦合；仅 10 秒自动挂起影响复现 |

### 4.3 修复方案

**档一 · 零风险配置**
- **方案 A（首选）**：在 `/init.bigfish.rc` 追加
  ```rc
  on resume
      ifup eth0 2>/dev/null
      start iprenew_eth0
  ```
  （用 `dhcpcd -n` 续租，失败自动回退 DISCOVER；`ifup` 对已 up 接口无副作用）
- **方案 B**：修 `init.bigfish.rc:94` 语法 —— 把 `sdcard_r` 并入上一行 `group` 列表。风险无。
- **方案 C**：属性加固（`ro.hw.sys.net.eth.redhcp=1` 已有；`persist.hdmi.suspend.enable 0` 需产品确认）
- **方案 D**：清陈旧锁 `/data/local/tmp/wifi_recover.lock`（2016-05-08 残留空目录，`mkdir` 失败即视为"已锁"→ 自愈永久失效，日志每 15s 空转）
- **方案 E**：MTU 显式 1460（可选）

**档二 · 需改二进制/APK（仅档一无效时）**
- **方案 F**：改 `HiRMService.apk` 让 `prepareResume` 受属性门控 / smali 补丁（风险中，PM 核心逻辑，无远程回滚）
- **方案 G**：改 `libhi_msp.so` 放宽唤醒源（风险高，PMOC 域可能不生效，**不建议**）

### 4.4 安全约束（重要）

**S3 之后只有红外遥控能唤醒，且 eth0/USB 都不能唤醒。** adb 唯一通道是 eth0 的 TCP 5555，S3 后必然中断；若唤醒后网络未按预期恢复，**将彻底失去远程控制**。因此：
- 本次**未执行真实休眠实测**（`echo standby > /sys/power/state`），已改为把全部诊断落盘到设备 `/data/local/tmp/pre.*`。
- 方案 A/B/D 均**不触发休眠**，改完重启即可验证，风险可控。
- 若最终要验证 S3，**必须先确保有物理/红外唤醒手段**（设备存在 `/dev/ttyAMA0`，但当前无物理串口接入）。

## 6. 结论

三个问题的**共同模式**是"状态切换时刻的同步缺失"，而非硬件损坏：

- HDMI：**热插拔后不同步 DISP 虚拟屏** → 声明 1080p、画布 720p；
- S3：**resume 后不重建网络栈** → 驱动在、IP 丢、adb 断；
- 视频：**框架 codec 表未注册 hevc** → 底层能解、上层找不到。

这三处都是"**有正确的组件，缺正确的胶水**"型缺陷，均可用配置或小范围二进制补丁修复，**不需要更换硬件**。
